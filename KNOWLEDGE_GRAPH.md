# BibleFlow Knowledge Graph

## Architecture Decisions
1. **Frontend Framework**: React 18 with TypeScript and Vite. Chosen for component-based UI, strong typing, and fast build times.
2. **State Management & Data Fetching**: React Query (`@tanstack/react-query`) is used for server state caching, while standard React Context/Hooks handle local state.
3. **Graph Engine**: `@xyflow/react` (React Flow) v12. Chosen to provide the interactive, drag-and-drop node-based visualization of Bible verses and theological topics.
4. **Backend as a Service (BaaS)**: Supabase (PostgreSQL + Real-time subscriptions). Handles the database (`topics`, `verses`, `connections`, `topic_links`) and provides real-time updates so changes are instantly synced across clients.
5. **Routing**: React Router DOM v6 for client-side routing. The data-heavy `/map` route is lazy-loaded so its versioned historical catalog does not inflate the initial application bundle.
6. **Styling**: Tailwind CSS 3.4 for utility-first, responsive, and customizable styling.
7. **External APIs**: `bible-api.com` is used for fetching KJV Bible texts securely and freely without requiring API keys. Verse text is now stored as multi-line strings with `[ch:v]` prefixes (e.g. `[3:16] For God so loved...`) enabling per-verse line display.

## Core Entities & Data Models
- **Topics**: Represents a theological concept or study theme (e.g., "Faith", "Salvation"). Has a name, description, and color.
- **Verses (Nodes)**: Represents a specific Bible verse or custom verse selection. Belongs to a Topic. Contains the biblical text (multi-line `[ch:v] text` format), reference (book, chapter, verse_start, verse_end), a personalized note, and its XY coordinates for the graph. `chapter=0` is a sentinel value indicating a custom (non-contiguous) verse selection. They have types: `main`, `supporting`, `contrast`, `context`.
- **Connections (Edges)**: Represents relationships between verses within a topic graph. Types include `supports`, `contrasts`, `explains`, `fulfills`, `references`.
- **Topic Links (Cross-Topic Edges)**: Represents macroscopic relationships between overarching Topics (e.g., Topic A leads to Topic B).
- **Entities**: Represents biblical people, places, nations, events, objects, or concepts. Has a type, description, optional metadata, `timeline_period_id` (nullable FK to timeline_periods), `atlas_x`/`atlas_y` for positioning on the People Atlas canvas, and `lat`/`lng` (nullable) for geographical coordinates on the Biblical Map.
- **Entity Mentions**: Bridge table linking Entities to Verses. Captures the specific context of the mention (e.g., 'speaker', 'subject', 'location') and optional anchor words in the verse text.
- **Entity Relationships**: Directed or symmetric assertions between entities with an extensible definition, preserved legacy `type`, notes, optional status/period/lineage/parentage metadata, and multiple structured Scripture evidence records. Different assertions between the same pair are supported. See Relationship Atlas below.
- **Timeline Periods**: User-created time periods stored in `timeline_periods` table. Each has a name, color, `sort_order` (controls vertical stacking), and `band_height` (px height of the canvas band, default 300, min 120). Rendered as colored background bands on the People Atlas canvas. Supports insert-at-position (beginning, middle, end) and move-up/move-down reordering via `reorderTimelinePeriods()` batch update.
- **Historical Places**: A versioned public-data catalog generated from OpenBible.info Bible Geocoding Data, separate from user-created `Entity` places. Each of the 1,335 mappable ancient records keeps a stable OpenBible ancient id, canonical and translation names, complete cataloged Scripture references, place type, a primary point and its precision, alternate geographic identifications, and a 0–1000 time-weighted confidence score. Distinct ancient records remain distinct even when they share the same representative modern point.

## Component Map & Data Flow
- **AppShell**: Main layout wrapper including the `Header` and `Sidebar`. Its responsive shell keeps a compact five-destination navigation rail visible on phones, preserves safe-area padding, and turns shared side panels into bottom sheets below the `sm` breakpoint.
- **Dashboard (`/`)**: Lists all Topics using `TopicGrid` and `TopicCard`. Uses `useTopics()` hook.
- **TopicGraphView (`/topic/:id`)**: The main interactive React Flow canvas. Renders `VerseNode` components and `ConnectionEdge` components. Uses `useVerses()` and `useConnections()` for state and Supabase sync. Entity tags (`EntityChipBar`) are embedded directly into verse nodes. On narrow screens its controls stack into a dedicated, icon-first toolbar while the canvas remains available beneath it.
- **TopicsNetwork (`/topics/network`)**: Macro-level view of all topics connected to each other via cross-topic links.
- **SearchPage (`/search`)**: Global search interface for finding verses across topics.
- **EntityExplorer (`/entities`)**: Dedicated interface for browsing, filtering, and managing all entities. Includes `EntityDetailSidebar` to show where entities are mentioned across all topics. Uses `useEntities()` and `useEntityMentions()` hooks.
- **PeopleAtlas (`/atlas`)**: A React Flow canvas showing all tagged people as a family tree diagram over user-created timeline bands. Sub-components: `PersonNode` (draggable person cards), `RelationshipEdge` (labeled lines connecting people), `TimelineBands` (colored SVG background bands with per-period heights and drag-to-resize handles), `CreatePeriodModal` (supports insert-at-position and move-up/down reordering), and the shared `RelationshipEditor`/`SetParentsModal`. Uses `usePeopleAtlas()` hook which orchestrates `useEntities()`, `useTimelinePeriods()`, and relationship queries. Dragging a person into a timeline band auto-assigns them to that period using cumulative Y-offset calculation. Period heights are persisted to Supabase via `band_height` column.
- **MapAtlas (`/map`)**: An interactive, full-viewport Leaflet map centered on the biblical world. A collapsible left study dock contains search and the Explore, Passage, Journey, and Library accordions; on phones it starts as a compact bottom control rail and expands into a bottom sheet, preserving a usable map viewport. `MapSearchBar` searches only local biblical, saved-study, and vetted historical-territory records.
  - **Canonical Biblical Locations**: `scripts/import-openbible.mjs` converts the pinned OpenBible JSONL revision into `src/data/generated/openBiblePlaces.json`: 1,335 mappable ancient records from 1,342 source records. `biblicalPlaces.ts` derives book indexes and search fields while preserving stable source ids, place types, all cataloged verse references, alternate resolutions, precision, and confidence. Ancient identities are never collapsed just because they share a modern coordinate.
  - **All-record clustering and filters**: Every record matching the current book/coverage/type filters is represented at every zoom. `mapClustering.ts` groups nearby records in projected screen space; close zoom retains clusters only for truly co-located records, whose marker opens a selectable list. This replaces the old importance-tier renderer that silently hid minor records until high zoom.
  - **Place evidence record**: Selecting a single marker, a co-located result, a search result, or a passage result opens `HistoricalPlaceDetails`. The folio-style panel shows translation names, the complete source reference count (first 36 initially), coordinate precision, primary and alternate identifications, confidence scores, and pinned OpenBible attribution.
  - **Historical peoples and kingdoms**: Search Canaanites, Ammonites, Edomites, Moabites, Philistines, Arameans, Assyrians, Babylonians, or the Hittite kingdom to display sourced geometry in a non-interactive pane beneath pins. The Hivite Gibeonite towns and Amorite historical centers instead render named site lenses; these show documented locations without inventing ethnic/imperial borders. The evidence card labels each evidence mode, references its source, and keeps genuinely unresolved groups (including Perizzites and Girgashites) explicit rather than fabricated.
  - **Book lens and study areas**: A book selector combines the catalog's full cited-place index with a local-KJV scan for literal place names across the selected book (including KJV spelling variants such as Askelon/Ashkelon). Zoom-aware clusters preserve map movement and readability, while deliberately approximate historical study areas remain subtle (and are not modern political borders).
  - **Passage lens**: `PassageMapPanel` accepts a book, chapter, and optional verse range; the map loads the local KJV text, matches literal biblical names plus cataloged references, then temporarily shows only the matched indigo pins. The sidebar and active study badge give exact selected-passage verse references, and clearing restores the normal map.
  - **Travel insight**: `TravelInsightPanel` selects any two built-in or saved places and shows a teal A→B map layer. `travelInsights.ts` calculates a haversine distance, a 16–22 km/day walking range, terrain context, and direct/overland/historical-corridor study options. These are deliberately labeled estimates rather than modern directions or asserted reconstructed routes.
  - **Bible-aware Search**: Exact canonical names and alternate biblical names rank before partial matches; cited references are searchable. There is intentionally no Nominatim/general-world fallback, preventing an ambiguous biblical query from opening a modern street abroad.
  - **Search Result Pin**: On selection, `handleFlyTo` drops a styled `divIcon` label marker and opens the full historical-place evidence record for catalog results. Amber styling identifies catalog locations; indigo identifies personal saved locations. The temporary search label dismisses on any map click.
  - **Basemap**: Bundled Natural Earth physical geography by default, with an explicit OpenStreetMap.de modern-reference alternative; neither needs a paid provider key.

## How It Works
1. **Initialization**: The App starts up at `main.tsx`, wrapping the application in `QueryClientProvider` and `BrowserRouter`.
2. **Topic Creation**: Users create a topic which is saved to Supabase via `useTopics()`. 
3. **Verse Addition**: Within a Topic, users add a verse. The app queries `bible-api.com` for the text, then saves the verse entity to Supabase via `useVerses()`. 
4. **Graph Interaction**: Verses appear as nodes on `VerseFlowCanvas`. Dragging nodes updates their `position_x` and `position_y` in real-time, syncing to Supabase. Drawing lines between nodes creates `Connections`.
5. **Real-time Sync**: Supabase channels listen for database changes, triggering React Query invalidations or state updates, ensuring any client looking at the same graph sees real-time movements and additions.

## Full Features of the Website
1. **Topic-Based Organization**: Create, manage, and color-code theological topics.
2. **Interactive Graph Visualization**: Draggable, auto-saving Bible verse nodes mapped visually on an infinite canvas.
3. **Semantic Verse Connections**: Draw directed lines to define doctrinal relationships (supports, contrasts, explains, fulfills, references).
4. **Contextual Entity Tagging**: Tag people, places, events, and concepts directly onto verses to build an interconnected biblical knowledge graph.
5. **Topic Network View**: A global visualization of how broad theological topics interrelate.
6. **Bible Integration**: Auto-fetches KJV text, validates verse structures, supports verse ranges and custom non-contiguous verse selections (Python-style fancy indexing). Verse text is stored as multi-line `[ch:v] text` format and rendered line-by-line in nodes with superscript verse numbers.
7. **Global Search & Discovery**: Search through all verses and personal notes with debounced grouping.
8. **Export & Sharing**: Export any topic graph as a high-quality PNG image.
9. **Dark Mode**: Complete support for system-preference dark mode.
10. **People Atlas**: Family tree diagram + vertical timeline with user-created colored background bands. People are draggable nodes, relationships are labeled edges, and dragging a person into a timeline band auto-assigns them to that period.
11. **Biblical Map**: Bible-first, full-canvas historical-place explorer with an all-record clustered catalog; book/coverage/place-type filters; stable OpenBible identities; evidence-aware place records with alternate identifications and confidence; a KJV-backed passage-to-map lens; transparent distance/travel estimates; subtle approximate study-area overlays; biblical-name/reference search that never falls back to modern addresses; saved-place management; and separately labeled person-route visualization.
12. **Mobile-first study workflow**: Phone-sized navigation exposes every primary destination; forms, confirmations, and entity details use safe-area-aware bottom sheets; interactive canvases trim secondary chrome, retain large touch targets, and keep their core pan/zoom/drag workflows available.

## Historical era map model (September 2026)

The map now offers twelve discrete curated study periods. These are canonical static era IDs, independent of user-created People Atlas timeline UUIDs. Thirteen named narrative snapshots keep the displayed scope explicit; Judges has separate scouting and chapter 19 contexts. Dates use qualified verbal chronology, not inferred occupation intervals or an evenly scaled year axis. No Supabase migration or historical write is involved.

`historicalEraContent.ts` adds 73 reviewed-in-source place annotations, three scoped name/identity assertions, thirteen site contexts and seventeen ordered itineraries to the pinned OpenBible catalog. “Reviewed” is the implementation’s editorial source check, not independent specialist review. All context layers use narrative-attested candidate sites; no reconstructed imperial frontier is asserted. Missing annotations mean unclassified. Exact joins preserve separate ancient identities, including Jebus/Jerusalem. The label resolver applies scoped snapshot/era names before book-lens/canonical names; Laish and Sebaste demonstrate qualified name changes.

`historicalEraResolver.ts` owns normal era/book/type/coverage intersection and deduplicated passage, historical-route and explicit-focus overrides. Passage results retain their reading selection across era changes. Search ignores map-density filters, follows the era/book scope, and provides a deliberate all-eras/all-books escape. Undated general territories remain inspectable but their outlines are suppressed in era mode. Selected evidence stays open when a marker leaves the filters. Personal saved routes, draft point names and study travel estimates do not acquire dates or get rewritten.

The Leaflet map is retained while dedicated layer groups update. Area/site context, journeys and persistent names are independent; Places hides catalog and passage pins/labels. Label collision avoidance does not discard catalog identities. Rendering effects do not fit the camera. Explicit Fit era and passage application calculate padding from actual dock/detail/control bounds; era changes stop stale search flights and cancel delayed pins. Passage/book operation guards prevent late responses from restoring discarded reading selections.

The era selector UI, including the dropdown, previous/next buttons, slider, desktop timeline and phone chip, has been removed. Historical context still resolves existing era links and saved preferences. Era/snapshot query parameters override validated local preference, history removal means All eras, and invalid explicit era links safely return to All eras. Versioned localStorage is optional and guarded. Reset clears its stored era preference and era/snapshot parameters while preserving unrelated query parameters.

Physical geography is the default map backdrop: pinned Natural Earth land plus the Sea of Galilee and northern Dead Sea, with no modern political/city labels. It is modern schematic physical reference, not ancient coastline reconstruction. The explicit Modern map option retains OSM.de tiles. Both historical content and the physical asset stay inside lazy map chunks and the production precache; external raster tiles are not promised offline. Source provenance, release limits and verification are recorded under docs/historical-era-*.md.

## Performance implementation (September 2026)

Dashboard startup excludes React Flow and non-dashboard routes; the topic graph provides its own ReactFlowProvider and PNG export loads only when requested. Each graph route imports its required React Flow CSS. The verse canvas reuses memoized node/edge builds; People/network graph joins use maps. Verse and person positions save once at drag-stop, avoiding shared debounces that dropped quick successive moves.

Topic counts use a React Query cache keyed by sorted topic IDs and one `get_topic_counts` RPC after migration 009; older databases fall back to four topics at a time. Entity tags load through a topic-filtered joined query in 500-row pages instead of one request per verse. Search requests are aborted when superseded; migration 009 adds trigram indexes matching the existing substring search semantics.

The Bible worker indexes books and chapters once after its shared fetch. Map book matching normalizes verse text once, caches catalog names by record, and uses first-word candidates before exact phrase matching. Clustering appends to buckets rather than copying each bucket on every insertion. Map marker/name redraws coalesce moveend/zoomend in an animation frame with cleanup. See docs/performance-audit.md for measured scope and remaining profiling limits.

## Relationship Atlas and search (November 2026)

People Atlas now has Family and All relationships views. Its open relationship vocabulary includes priest of, prophet of, prophet to, concubine of, political/service/geography roles and arbitrary user-defined labels. Definitions provide category, symmetry, optional inverse label and explicit parent direction; they do not infer gender or equivalence from arbitrary words. Multiple assertions between a pair can share an expandable visual bundle while retaining their IDs, direction, context and evidence. Entity details render the complete source-to-target statement so incoming relationships never reverse meaning.

Migration 010 adds `relationship_definitions`, `relationship_evidence`, and nullable definition plus contextual metadata fields on relationships. It preserves legacy strings, descriptions, route order and person positions, classifies only exact known labels, and never marks old parent labels as direct/biological facts. Invoker RPCs save a relationship plus evidence atomically and add/confirm selected direct parents in one transaction. Direct-parent cycles and duplicate assertions are checked within serialized Atlas writes. Parent confirmation reuses compatible records without discarding their descriptions or evidence; other parent assertions are not removed. The migration must be deployed separately; legacy reads remain available and save failures preserve form values when it is missing.

Confirmed explicit direct-parent pairs with compatible parentage nature and relationship period derive a small junction with orthogonal branches to their shared children. Junctions are presentation nodes, have fixed measured dimensions and encoded stable IDs, never persist as entities and never receive timeline assignments. Single-parent, ancestral, inferred/disputed, and ambiguous three-parent contexts stay separate. Marriage and concubinage remain independent labeled assertions. Manual node positions are preserved; derived routing follows measured dimensions and live dragging. Positions save per entity with optimistic cache updates and rollback, and label/evidence updates refresh without relying on ID-only change keys.

The Atlas can reveal place/nation/event/object/concept endpoints. Group, institution and divine-entity subtypes are explicit metadata on concepts. Migration 010 removes name/type uniqueness: UUIDs identify entities, qualifiers distinguish same-name people, and aliases are explicit metadata. Atlas creation and verse tagging prompt for deliberate same-name identity creation instead of merging records.

Local indexed search covers recorded names, aliases, qualifiers, notes, relationship labels/endpoints and structured Scripture evidence. Results distinguish entities, relationship types, individual assertions and references; book abbreviations normalize to canonical names. Search and editor pickers accept custom labels. Selecting a result reveals its endpoints and fits the camera; typing and clearing do not move or save nodes. A temporary reveal preserves active filters and can be dismissed. Filters cover category, exact type, entity type, relationship period (optionally including undated assertions) and status. People can be focused to immediate neighbors. Existing global verse search is unchanged. All entity, relationship, definition and evidence reads are paginated.

The Atlas keeps the shared paper/ink visual system, with a persistent search toolbar, collapsible phone filters, readable direction/category/status labels, and a desktop details pane or phone lower pane that leaves the canvas visible. Editors use the shared accessible Modal, searchable selectors, async status and retained input on failure. The general map continues consuming the original relationship CRUD methods and `sort_order`. Browser fixtures and disposable PostgreSQL tests are documented in docs/relationship-atlas-verification.md.
